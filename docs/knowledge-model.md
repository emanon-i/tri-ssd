# 知識モデル

Tri-SSD が扱う知識の置き場・寿命・更新契機を定める。配置判断の唯一の出所（SSOT）。
書き方は [記載規約](writing-rules.md)、機械処理の仕様は [アーキテクチャ](architecture.md) が受け持つ。

## 置き場

情報は抽象度ではなく**何が変わると変わるか（更新契機）と寿命**で置き場を決める。

| 置き場 | 書くもの | 更新契機 | 寿命 | 読まれ方 | 場所 |
|---|---|---|---|---|---|
| Goal | 目的・成功状態・原則・やらないこと | 目的が変わる | プロジェクト全体 | context で常に全文 | `docs/goal.md` |
| Docs | あるべき状態（現在または将来）: 要求・構成・契約・インターフェース・データ・運用規則・制約と、その選定理由と却下案 | 要求・設計の判断が変わる | 置き換えられるまで | context でセクション単位 | `docs/` 配下（`docs/goal.md` を除く） |
| Tasks | Docs と現実の差分を解消する作業: 目的の状態・受け入れ条件・検証記録 | 作業が進む | 完了まで（完了後は履歴） | 着手時に全文 | `tasks/`（完了・中止後 `tasks/archive/`） |
| 作業メモ | 作業中の発見・仮説・調べたこと | 作業が進む | Task の完了まで（Task と一緒に退場） | Task の一部として | Task ファイルの `## メモ` |
| NOTES | 現在位置・次にやること・未決事項 | セッションの終わり | 次の上書きまで | セッション開始時 | `NOTES.md` |
| 常に守る規則 | どの作業でも守る短い規則（例: 全クエリを利用者 ID で絞る） | 規則が変わる | プロジェクト全体 | 毎回（エージェントが常に読む） | エージェントの指示ファイル（`CLAUDE.md`・`AGENTS.md`）。1規則1行、理由は Docs へのリンク |
| CHANGELOG | Docs の意味のある変更: 何を・なぜ（関連 Task） | 変更が確定する | 永続（追記のみ） | 経緯を調べるときだけ | `CHANGELOG.md` |

`docs/`・`tasks/`・`NOTES.md`・`CHANGELOG.md` 以外は Tri-SSD が読まない。一時的な調査や共有しない材料は、git 管理外の `tmp/` に置く（`.gitignore` に `tmp/` を書く。Tri-SSD は作らない）。

どの置き場にも、内容が不要になる時点（寿命の終わり）がある。終わりの無い置き場（受け箱・ログ）は作らない。溜まる場所が無ければ、溜める仕組みも整理する仕組みも要らない。

### 名前の規則

| 規則 | 例 |
|---|---|
| ルートに置く 1 枚だけのファイルは、慣習どおり英大文字の名前にする | `CHANGELOG.md`・`NOTES.md` |
| 複数のファイルを入れるフォルダは、英小文字で中身を表す名詞にする | `docs/`・`tasks/`・`tasks/archive/` |
| フォルダの中のファイルは英小文字のハイフンつなぎにする。ID を持つものは ID を先頭に置く | `docs/architecture.md`・`tasks/T-0005-tag-search.md` |
| フォルダは寿命で分ける（作業中か、終わったか）。完了か中止かは frontmatter の `status` が持つ | `tasks/archive/` に `status: done` と `status: dropped` が並ぶ |

## 判定フロー

新しい情報は上から順に判定し、最初に該当した置き場に書く。

1. 実現手段を1つも決めなくても真な、目的・成功の条件か → **Goal**
2. 今の作業が終わっても真であり続ける、システムのあるべき姿か、その姿を選んだ理由か → **Docs**
3. あるべき姿と現実の差分で、完了を観測で判定できる作業か → **Task**
4. 過去に何を変えたか・なぜ変えたかか → **CHANGELOG**
5. どれでもない（作業中の推測・調査メモ） → その **Task の `## メモ`**。再開のための現在位置 → **NOTES**。どの Task にも属さない気づきは、その場で Task にするか捨てる

| 迷いやすい例 | 置き場 |
|---|---|
| 「検索は 500ms 以内」 | Docs（REQ）。手段に依存しないが Goal ほど長命でない要求は Docs に REQ として置く |
| 「検索は FTS5 で実装する」 | Docs（構成） |
| 「FTS5 は 2 文字のクエリに一致しない（実測）」 | 検証済みで今後も真なら Docs、調査途中なら Task の `## メモ` |
| 「AC1 のテスト 8 件 PASS」 | Task の検証記録（`task verify` が記録する） |
| 「JSON 保存から SQLite に変えた」 | 新しい状態を Docs に書き、変えた事実と理由を CHANGELOG へ |
| 「次は `T-0006` から再開」 | NOTES（`NOTES.md`） |
| 「全クエリを利用者 ID で絞る」 | 常に守る規則（指示ファイルに1行。詳細は Docs のセキュリティ文書） |

## Docs の分類

Docs はファイル名や階層を固定しない。更新契機と参照単位が同じものを同じファイルに置く。

| 種類 | 内容 | 典型的な更新契機 |
|---|---|---|
| 要求 | REQ 単位の要求（手段に依存しない「〜できる」） | 要求の追加・変更 |
| 構成 | 技術選定と理由・構成・エラー処理方針・テスト戦略 | 技術判断 |
| 契約 | API・CLI・画面・入出力・機能単位の「やること / やらないこと」 | インターフェースの判断 |
| データ | 概念モデル・ライフサイクル・整合性の基準（カラム定義の正はコード） | データ設計の判断 |
| 運用 | デプロイ・バックアップ・定期処理・監視 | 運用判断 |
| 手順 | 繰り返し実行する作業手順（将来 Skill 化の候補） | 手順の改善 |

- 判断が分かれた箇所には、その文書に `## 選定理由と却下案` の節を置き、選んだ理由と採らなかった案を書く。今も成り立つ説明なので、却下した案に触れても履歴汚染にはならない
- 判断に至った出来事（何が起きて変えたか）は CHANGELOG に書く
- 履歴そのものを書く文書（移行前の ADR など）は frontmatter に `kind: history` を付ける

分割の基準:

- **更新契機・担当範囲が違うなら分ける**。サイズだけを理由に分けない（context がセクション単位で取得するため）
- 1ファイルが約 4000 トークンを超えたら、重複・古い記述の残存を疑い、次に更新契機での分割を検討する
- コードが正となる詳細（カラム定義・関数一覧・設定値の全量）は Docs に複製せず、パスで参照する

## コードと Docs の差分

Docs は満たすべき状態、コードは実際の状態を知るための主要な証拠である。両者が食い違ったら次のどれかに分類する。

| 状況 | 扱い |
|---|---|
| Docs が正しく、コードが未達 | Task を作り、Docs の該当記述に `（計画: T-nnnn）` を付ける |
| Docs が誤り（仕様の誤り） | Docs を正しい状態に書き換え、意味が変わるなら CHANGELOG に記録 |
| 設計が未確定 | 該当記述に `（未確定）` を付ける。決めるべき人・材料を NOTES に残す |
| 意図的に後回し | `（保留）` を付ける。Task は作らない |
| 前提が未検証の推測 | `（未検証）` を付ける。検証が必要なら検証 Task を作る |

マーカーのない記述は「現在の実装がこの状態を満たしている」ことを意味する。
Task が完了したら対応する `（計画: T-nnnn）` を外す（外さないと完了ゲートを通らない）。

## Task

Task は「現実をあるべき状態へ近づける」検証可能な単位である。

- **粒度**: 1つの観測可能な状態変化。1〜3 セッションで終わる
- **AC**: 「目的の状態のどの要素が欠けても、少なくとも1つの AC が必ず落ちる」を満たす最小の数（1つの AC で複数の要素を確かめてよい）。各 AC は観測可能な振る舞い1つと、その検証手段（`検証:` 行のコマンド、または `手動:` の確認方法）
- **判断**: 方法の選択で判断が分かれたときだけ `## 判断` 節に「選んだ方法・やめた案・理由」を書く
- **報告**: 人間はコードの代わりに `task report` を読む。報告は目的の状態・満たす仕様・検証記録・判断・差分・CHANGELOG から組み立て、新しく書かせない
- **状態**: `open` → `active` →（`blocked`）→ `done` または `dropped`。完了・中止したファイルは `tasks/archive/` へ移り、履歴として context の対象外になる（後の変更で検証コマンドが古くなっても直さない）
- **完了**: 自己申告ではなく完了ゲートで判定する（[アーキテクチャ](architecture.md#完了ゲート)）。テスト成功は AC の充足を意味しない。各 AC の記述と検証結果の対応をエージェントが確認する
- すべての差分を Task にしない。上の差分分類で Task になるのは「Docs が正しく、コードが未達」だけ

## 作業メモと NOTES

- 作業メモは Task ファイルの `## メモ` に1〜3行で書く。Task が完了すると `tasks/archive/` へ移り、context の対象から外れる
- 完了前に、メモのうち今後も真な事実は Docs へ、全作業で守る規則は指示ファイルへ移す
- NOTES は追記せず上書きする（現在位置は常に1つ）。Task に属する進み具合は Task に書き、NOTES には Task をまたぐ現在位置・次にやること・未決事項だけを書く

## CHANGELOG

- 記録する: 要求・設計判断・契約の意味のある変更、利用者に見える機能の追加・修正
- 記録しない: 意味を変えない文言修正、Task の作業経過
- 形式は Keep a Changelog。`[Unreleased]` の下に種別（Added / Changed / Deprecated / Removed / Fixed / Security）ごとに追記する
- 既存の記録は書き換えない（リリース時の版見出しへの移動を除く）

## ID

| 接頭辞 | 対象 | 定義される場所 |
|---|---|---|
| `REQ-nnnn` | Goal・Docs の規範項目（要求・契約） | Goal・Docs の見出し |
| `T-nnnn` | Task | `tasks/` の frontmatter `id` |
| `PH-nnnn` / `F-nnnn` | 旧 Tri-SSD のフェーズ・機能（移行互換） | Task ファイル |

- 番号は再利用しない（永久欠番）。採番は全文書・完了 Task・NOTES・CHANGELOG に現れた最大番号の次（`tri id`・`task new`）
- すべての規範項目に ID を付ける必要はない。Task や他の Docs から安定して参照される項目にだけ付ける

## 知識グラフ

文書間の関係は手で索引を維持せず、ID・リンク・frontmatter・見出し・コードパスから毎回導出する（[アーキテクチャ](architecture.md#知識グラフ)）。

## 選定理由と却下案

| 選んだこと | 理由 | 採らなかった案 |
|---|---|---|
| 置き場を更新契機と寿命で分ける | 抽象度（要件・構成・フェーズ）では置き場が決まらず、変更前の記述や完了した計画が残り続ける | L1〜L3 の固定階層。フェーズ計画は完了で腐る |
| 取り締まる仕組みを足さず、置き場を寿命に合わせる | 溜まる場所が無ければ、溜まった情報を整理する仕組みも要らない | ノートの受け箱と整理候補の提示、読み込み記録のフック。試行で効果を示せなかった |
| NOTES を上書きの 1 枚にする | 次のセッションが読むのは現在位置だけ。積み上げると読まれなくなる | 日付ごとの記録の積み上げ。git 管理外の個人用の置き場（一人で使う道具では使う場面が無い） |
| `tasks/` と `NOTES.md` を `docs/` の外に置く | `docs/` を「あるべき状態」だけにし、例外の無い規則にする | `docs/tasks/`・`docs/notes/` に置き、予約領域として除外する |
| 選定理由を各文書の節に書く | 理由は経緯ではなく今も成り立つ説明で、対象の記述と同じ場所で読める | ADR を別に書く。理由が対象から離れ、経緯と混ざる |
