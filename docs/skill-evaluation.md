# Skill の評価

3 スキルについて、(1) 呼ぶべき依頼で呼ばれ、呼ぶべきでない依頼で呼ばれないか（発火）、(2) 呼ばれたときに Skill 無しより良い結果を出すか（成果）を `claude plugin eval` で測る。

## 方法

手法は次の資料に従う。

- 発火の評価: [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)・[agentskills.io の説明文の最適化](https://github.com/agentskills/agentskills/blob/main/docs/skill-creation/optimizing-descriptions.mdx)
  - 実際に打たれそうな依頼を使い、呼ぶべきでない側は語や文脈が近いものにする
  - 学習 60%・検証 40% に層別で分けて固定し、説明文は学習側の失敗だけを見て直し、検証側で報告する
  - 各依頼 3 回、発火率 0.5 以上を「呼ばれた」とする
- 成果の評価: [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)・[Claude Code の plugin eval](https://code.claude.com/docs/en/plugin-evals)
  - 経路ではなく結果（最終ファイル）を採点する。機械で判定できないものだけ LLM（haiku、3 票の多数決）で判定し、一部を実物と照合する
- 統計: [A statistical approach to model evaluations](https://www.anthropic.com/research/statistical-approach-to-model-evals)
  - 単位はケース（実行ではない）。スキルあり・なしは同じケースで比べ、ケースごとの差の平均に 95% 信頼区間（t 分布）を付ける。割合には Wilson の 95% 信頼区間を付ける

### ケース

| 種類 | 置き場 | 内容 |
|---|---|---|
| 発火 | `evals/trigger/queries.json` | 40 件（task 10・docs 10・setup 8・どれも呼ぶべきでない 12）。題材は linkbox（Tri-SSD 導入済み）・v5project（旧構成）・Tri-SSD でない小さな CLI。分割は作成時に seed 42 で決めて固定（学習 24・検証 16）。`evals/trigger/build.py` がケースを生成し、`summarize.py` が集計する |
| 成果（held-out） | `evals/heldout-*` | スキルごとに 2 件。出力を見る前に採点基準を書いてコミットし、固定した |
| 成果（dev） | `evals/` のその他 5 件 | 開発中に作ったケース。出力を見てから足した採点（`api-md-refers-not-duplicates`）を含むので、探索用として扱い、確証には使わない |

- 実行: 作業ツリーを `python scripts/install.py` で導入してから（Skill は PATH 上の `tri` を呼ぶ）、`claude plugin eval . --tag <trigger|heldout> --scaffold --allow-tools Bash Write Edit`。`.claude-plugin/plugin.json` は評価のために Skill を束ねるだけのもの。子セッションは既定のモデル（claude-sonnet-5-5）。Linux では Bash のサンドボックスに bubblewrap と socat が要る
- 採点はファイルの内容で行う（エージェントは Edit ではなく Bash で編集することも多いので、ツール呼び出しでは見ない）
- `tri check` の終了コードは eval では採点できないので、作業ディレクトリを残し（`--keep-temp`）、あとから実行して数えた

## 結果

### 発火

修正前の説明文（コミット 657dfc0）と現在の説明文を比べた（各依頼 3 回）。

| | 修正前 | 現在 |
|---|---|---|
| 学習（24 件）で正しく振り分けた依頼 | 23/24（0.80〜0.99） | 24/24（0.86〜1.00） |
| 検証（16 件）で正しく振り分けた依頼 | 16/16（0.81〜1.00） | 16/16（0.81〜1.00） |
| 検証の再現率・精度（task / docs / setup） | すべて 1.00 | すべて 1.00 |

- 両方の版が上限近くにあり、この依頼セットでは版の差を測れない。今後は悪化を検知する回帰の評価として使う
- 修正前の誤りは、Tri-SSD でないリポジトリでの「`--count-files` を実装して」で docs が 3 回中 2 回呼ばれたもの。現在の版では 0 回
- 現在の版の検証側では、setup を期待する 1 件で docs が 3 回中 1 回呼ばれた（多数決では setup）
- 開発中に、進行中の Task（`T-0005`）の範囲に触れる値の変更（「タグ補完の上限を変えたい」）で task が呼ばれる例を見つけ、説明文を直した（v6.0.1）。新しい依頼では同じ失敗は再現しなかった。失敗は進行中の Task と重なる状況に限られていた可能性がある

### 成果（held-out、スキルあり・なし各 3 回）

| ケース | あり | なし | 差 | なし側で落ちた採点 |
|---|---|---|---|---|
| task: 仕様と食い違うバグの修正 | 1.00 | 0.75 | +0.25 | Task を作って完了しない（3/3） |
| task: 引き継ぎ | 1.00 | 0.92 | +0.08 | 引き継ぎに日付付きの記録を積み上げた（1/3） |
| docs: 保持期間の変更 | 1.00 | 0.85 | +0.15 | CHANGELOG に記録しない（3/3）、data.md の古い値が残る（1/3） |
| docs: 未実装の要求の追加 | 1.00 | 0.50 | +0.50 | 実装する Task を作らない（3/3）、CHANGELOG に記録しない（3/3） |
| setup: 既存プロジェクトへの導入 | 0.93 | 0.20 | +0.73 | 導入の仕組みが無く、Goal・CHANGELOG を作らない（3/3） |
| setup: 移行のドライランだけ | 1.00 | 0.50 | +0.50 | 移行の計画を示せない（3/3） |

- 差の平均は +0.37（95% 信頼区間 0.11〜0.63、6 ケース）。3 回すべて満点（pass^3）のケースはスキルありで 5/6、なしで 0/6
- 差が出たのは、Tri-SSD の手順の成果物（CHANGELOG・検証証跡付きの Task・Goal と導入・移行）だった。コードの修正やテストの追加、値の置き換えと別の意味の同じ数字を残すことは、スキルなしでも同じようにできた（30 の採点のうち 18 は両方とも同じ結果）。バグ修正の LLM 採点は、両方の merge.py を読んで判定が正しいことを確かめた
- `tri check` は、ファイルを変えないドライランのケース（旧構成のまま）を除き、全実行でエラー 0（あり・なしとも）
- スキルありの失敗: 導入で Goal に「Python 標準ライブラリだけで動く」と実現手段を書いた（3 回中 1 回）

### 開発中に見つけて直した問題

dev のケースと試行で見つけ、原因側（スキルの文言・CLI）で直した。回数は少なく、修正後の 0 回は「起きにくくなった」以上を示さない。

| 問題 | 原因と修正 | 修正前 → 後 |
|---|---|---|
| Tri-SSD でないリポジトリで docs が呼ばれる | docs の説明に「docs/goal.md がある」の条件が無かった。条件を書いた | 2/10 → 0/12（dev）。発火評価の学習側でも 2/3 → 0/3 |
| プラグインのディレクトリへ cd して CLI を実行する | 共通コンテキストに、どこで実行するかが無かった。プロジェクトのルートで絶対パスのまま実行すると書いた | 2/18 → 0/39 |
| 適用まで任されても、移行の了承を求めて止まる | setup の手順に任された場合が無かった。そのまま適用すると書いた | 適用 9/10 → 6/6 |
| `migrate` がフォルダ形式のフェーズの機能を「検証記録」の節に入れる | CLI の不具合。機能の節を検証記録の前に置く（テスト付き） | — |
| `task verify` が「手動: …」に書いたコマンドを実行する | CLI の不具合。「手動」で始まる検証行はコマンドとして扱わない（テスト付き） | — |

## 限界

- 依頼とケースは作者が書いたもので、他の人による確認はしていない。題材は 3 つのフィクスチャだけ
- 成果の held-out は 6 ケースで、信頼区間は広い。dev のケースは確証に使っていない
- 子セッションのモデルは claude-sonnet-5-5 だけ。LLM 採点は haiku で、照合したのは一部
- 費用（eval の推定値）: 発火評価は 1 版あたり約 10 USD（40 件 × 3 回）、成果の held-out は約 3.2 USD（6 件 × あり・なし × 3 回）
