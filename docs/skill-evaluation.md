# Skill の評価

## 方法

`evals/` のケースを `claude plugin eval` で実行し、スキルあり（プラグインを読み込む）となし（プラグイン無しの同じエージェント）を比べた。

- **ケース**（題材は `tests/fixtures/linkbox` と `tests/fixtures/v5project` を各実行の作業ディレクトリに複製する）:
  - 発火すべき 3: `task-continue`（「`T-0005` の続きをやって」）・`docs-change-value`（「タグ補完の候補数の上限を 20 件に変えたい」）・`setup-migrate`（旧構成で「移行して」）
  - 発火すべきでない 2: `neg-question-in-tri-project`（Tri-SSD プロジェクト内での一般的な Python の質問）・`neg-docs-other-repo`（Tri-SSD でないリポジトリでの「ドキュメントを更新して」）
- **採点**: 機械で判定できるものは最終ファイルの正規表現・ファイルの有無・ツール呼び出しで判定し（エージェントは Edit ではなく Bash で編集することも多いので、編集はツール呼び出しでなく最終ファイルで見る）、文書とテストの中身の妥当性だけを LLM（haiku、3 票の多数決）で判定する。Skill の発火・プラグインのディレクトリへの cd・`tri check` の実行は、スキルあり側だけの指標として点数から外す
- **`tri check`**: eval はコマンドの終了コードを採点できないため、各実行の作業ディレクトリを残し（`--keep-temp`）、あとから `tri check` を実行して数えた
- **実行**: `claude plugin eval . --scaffold --allow-tools Bash Write Edit --runs 3`。子セッションのモデルは既定（claude-sonnet-5-5）。Linux では Bash のサンドボックスに bubblewrap と socat が要る

## 結果

最終版（スキルあり・なし各 3 回）。setup の行は、最後の修正（下の表の 4）の前の版で測り、修正後にスキルありだけ 6 回測り直した値を併記した。

| ケース | 発火したスキル（あり） | あり | なし | 差 | `tri check` エラー 0（あり / なし） | なし側で落ちた採点 |
|---|---|---|---|---|---|---|
| task-continue | task 3/3 | 1.00 | 0.43 | +0.57 | 3/3 / 3/3 | 完了（`_done/` へ移動）・検証記録・計画マーカーの除去・判断の記録が 3/3 で無い |
| docs-change-value | docs 3/3 | 1.00 | 0.75 | +0.25 | 3/3 / 3/3 | CHANGELOG の記録漏れと、api.md への値の重複が 3/3 |
| setup-migrate | setup 3/3 | 0.67（修正後 6 回で 1.00） | 0.00 | +0.67 | 2/3（修正後 6/6） / 0/3 | なし側は移行の仕組みが無く、構成の定義をユーザーに尋ねて止まった |
| neg-question-in-tri-project | なし 3/3 | 1.00 | 1.00 | 0 | — | — |
| neg-docs-other-repo | なし 3/3 | 1.00 | 1.00 | 0 | — | — |

- **発火の精度**（最終版）: 発火すべき 9 回はすべて正しいスキルが発火し、発火すべきでない 6 回は 0 回だった。スキルありの採点は全ケース平均 0.93、なしとの差の平均は +0.30（eval の `meanDelta`）
- **良くならなかった点**: 発火すべきでない 2 ケースは、スキルなしでも正しく振る舞うので差は 0。スキルの効果は、Tri-SSD の手順（完了ゲート・CHANGELOG・1つの事実は1箇所・移行）が要る場面に限られる
- **費用**: 試行を含めた全実行で約 12.9 USD（eval が出す定価換算の推定値）。全ケースをスキルあり・なし各 3 回で約 2.7 USD

## 見つかった問題と原因側の修正

測定で見つかった問題と、修正前後の回数。

| # | 問題 | 原因 | 修正 | 修正前 | 修正後 |
|---|---|---|---|---|---|
| 1 | 「上限を 20 件に変えたい」で docs ではなく task が発火し（または何も発火せず）、CHANGELOG の記録漏れと値の重複が残る | task の `when_to_use` が「文書の改訂だけなら docs」としか書いておらず、利用者は「文書」と言わずに値の変更を頼む | docs の発火語に「仕様の値を変えたい」を加え、task から仕様の値・方針の変更を docs へ振り分ける | docs の発火 6/10 | 9/9 |
| 2 | Tri-SSD でないリポジトリの「ドキュメントを更新して」で docs が発火する | docs の `description` に task・setup と違って「docs/goal.md がある」の条件が無く、`when_to_use` が一般的な語だけだった | 条件を `description` と `when_to_use` に書き、goal.md の無いリポジトリでは使わないと明記 | 誤発火 2/10 | 0/12 |
| 3 | プラグインのディレクトリへ cd して CLI を実行する | 共通コンテキストが CLI の絶対パスだけを示し、どのディレクトリで実行するかを書いていなかった。`tri` はカレントディレクトリを扱い、配布されたプラグイン自体も docs/goal.md を持つので、別のプロジェクトを操作しうる | 共通コンテキストに「プロジェクトのルートでこの絶対パスのまま実行する（cd しない）」を加え、`migrate` の案内も絶対パスにした | 2/18 | 0/39 |
| 4 | 依頼で適用まで任されても、移行の計画を示して了承を求めたまま止まる | setup の手順が「了承を得てから適用」だけで、任された場合を書いていなかった | 任されていれば計画を示してそのまま適用すると書いた | 適用 9/10 | 6/6 |
| 5 | `migrate` がフォルダ形式のフェーズの機能を `## 検証記録` の下に入れ、AC が読まれない（エージェントが手で直していた） | 統合時に `_phase.md` の末尾（検証記録の節）の後ろへ機能を足していた | 機能の節を検証記録より前に置く（CLI の修正とテスト） | — | — |

- 回数は、各版で行ったすべての実行（試行の 1 回実行と、切り分けのための 6 回実行を含む）を合計した。回数が少なく、1 回の差は偶然でも起こる。とくに 3 は修正前でも 18 回中 2 回と低頻度で、修正後の 0/39 は「起きにくくなった」以上を示さない
- 修正していない観察: task-continue で、引き継ぎに「AC1 は実装済み」とあるのにコードが空実装だった食い違いに気づき、実装してよいかを尋ねて止まった回が 1 回あった（同じ版の 3 回中 1 回。他の 12 回は実装して完了した）。食い違いの指摘自体は正しく、1 回のために手順を足すのは過剰と判断した

## 限界

- `claude plugin eval` の測定は 1 ケース 3〜6 回で、題材は 2 つのフィクスチャだけ。子セッションは既定のモデル（claude-sonnet-5-5）で、LLM 採点は haiku。発火の精度は 5 ケースの依頼文に対するもので、言い回しの幅は測っていない
