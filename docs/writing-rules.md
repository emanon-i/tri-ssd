# 記載規約

Tri-SSD の文書の書き方の正規ルール。どこに書くかは [知識モデル](knowledge-model.md) が受け持つ。

## 現在形で書く

Docs と Goal には**現在または将来のあるべき状態だけ**を書く。過去の状態・変更の経緯は書かない。

| 書かない | 書く |
|---|---|
| 当初は JSON 保存だったが、件数増加で SQLite に変更した <!-- tri:ok --> | 保存は SQLite に行う（経緯は CHANGELOG へ） |
| ~~5 秒ごとにポーリング~~ 3 秒ごとにポーリング <!-- tri:ok --> | 3 秒ごとにポーリングする |
| 現在は認証なしで動く（将来は OAuth） <!-- tri:ok --> | 認証は OAuth で行う。`（計画: T-0012）` |

- 変更するときは**追記せず置き換える**。古い記述・重複した記述は同じ編集で消す
- 経緯が必要なら CHANGELOG（何を・なぜ）か ADR（判断の背景）に書く
- 意図して過去に触れる行は行末に `<!-- tri:ok -->` を付ける（検査の対象外になる）

## 1つの事実は1箇所

- 同じ事実を2つの文書に書かない。正を1箇所に決め、他は ID・リンク・パスで参照する
- コードが正となる詳細はパスで参照する（例: スキーマの正は migration ファイル）
- 索引・ナビゲーションの複製はよい

## 参照単位で構造化する

- 見出しは「ある作業が一部だけ読む単位」で切る。context は見出し単位で文書を取得する
- 安定して参照される項目は見出しに ID を入れる（`## REQ-0004 タグ検索`）
- 他の文書の記述に依存するときは ID かリンク（`[整合性](data.md#整合性)`）で書く。依存が書かれていない関係は取得されない
- 作業範囲のコードは実在するパスをバッククォートで書く（`` `src/sync/merge.py` ``）。実在するパスだけが関係になる
- 表 > 箇条書き > 散文の順に使う。5 行を超える段落を作らない

## 文章

- 1文1事実。結論を先に書く
- 修飾語・前置き・言い換えを書かない。形容が必要なら数値で書く
- 図は Mermaid で描く（構成 `flowchart`・状態 `stateDiagram-v2`・ER `erDiagram`・時系列 `sequenceDiagram`）

## 機械契約

以下は CLI が機械的に読む書式。表記を揺らすと検出されない。Goal・Task・CHANGELOG の雛形は `templates/` が正（CLI の `init`・`task new` はこれを写す）。

| 対象 | 書式 |
|---|---|
| ID | `PREFIX-nnnn`（4桁）。地の文に書くと参照、バッククォート内は例示 |
| 状態マーカー（Docs） | `（計画: T-nnnn）`・`（保留）`・`（未確定）`・`（未検証）`（半角括弧・コロンも可） |
| frontmatter（Docs） | `code: [パス・glob]`（記述・統治するコード）・`depends: [ID・パス]`・`kind: adr\|history`（履歴の記述を許す） |
| frontmatter（Task） | `id`・`status: open\|active\|blocked\|done\|dropped`・`refs: [ID・パス#見出し]`・`code: [パス]` |
| 受け入れ条件（Task） | `## 受け入れ条件` の下に `- [ ] AC1: 振る舞い`。その直下に字下げして `- 検証:` とバッククォートで囲んだコマンド、または `- 検証: 手動: 確認方法` |
| 作業メモ（Task） | `## メモ`。作業中の発見を1〜3行。Task の完了と一緒に退場する |
| 検証記録（Task） | `## 検証記録`。CLI が AC ごとに最新の結果だけを書く（手で書かない） |
| 判断（Task・任意） | `## 判断`。方法の選択で判断が分かれたときだけ、選んだ方法・やめた案・理由を1〜3行 |
| 検査の除外 | 行末の `<!-- tri:ok -->` |

プレースホルダ表記は書式の定義に `nnnn`、文中の伏せ字に `xxxx` を使う。
