# 記載規約（Writing Rules）

Tri-SSD が生成するドキュメント（vision.md / foundation.md / interface.md / data.md / PH-xxxx）の**書き方**の正規ルール。
このファイルが記載規約の唯一の出所（SSOT）。**どこに書くか**は `layer-rules.md`（配置の SSOT）が受け持つ。

## 文章の原則

- **1文1事実。結論を先に**書き、根拠・補足は後ろに置く
- **余計な修飾語・前置き・言い換えを書かない**（「非常に」「しっかりと」「基本的には」等は削る。形容が必要なら数値で書く）
- 同じことを2回言わない。強調は繰り返しでなく **太字** で行う
- ドキュメントは AI エージェントが繰り返し読む前提 — 短いほどコンテキスト効率が良い

## 構造化の原則

- **表 > 箇条書き > 散文**の優先順で書く（列挙可能な事実は必ず表か箇条書きにする）
- 見出しは**参照単位**で切る（あるスキルが一部だけ読む単位＝見出し。gen-code が「確認済みの前提」だけ読める構造にする）
- 散文の壁（5行超の段落）を作らない

## 図の規則

図はすべて **Mermaid** で描く。ASCII アートの図は使わない。

| 図の種類 | Mermaid 記法 |
|---|---|
| 構成図・依存関係 | `flowchart` |
| 画面遷移・状態遷移 | `stateDiagram-v2` |
| データ関係（ER） | `erDiagram` |
| 時系列・シーケンス | `sequenceDiagram` |

（ディレクトリツリーの表示は図ではないためテキストのままでよい）

## SSOT の原則

- 同じ事実を2つのファイルに書かない。**正を1箇所**に決め、他からは ID（REQ-nnnn 等）またはパスで参照する
- スキーマのカラム定義の正は実装コード（layer-rules「スキーマ定義 vs データ設計」参照）
- 索引・ナビゲーション（在り処マップ・ポインタ行）は複製してよい

## コンテキスト効率

- 1ファイル **300行を超えたら分割を検討**する（分割の判断・分割先は layer-rules「ファイル分割ルール」に従う）
- 「読み手のスキルが全文を読む必要があるか」を分割判断の軸にする（一部しか読まないなら分割候補）

## 機械契約マーカー（正確に再現する）

以下はエージェントが**機械的に検出・更新する契約**。表記を揺らすと検出されない:

| マーカー | 書式 | 読み手 |
|---|---|---|
| 未確定箇所 | `<!-- TODO: 要確認 -->` | gen-code が実装前に検出 |
| 未確認の仮定 | 付与時 `（未確認・要検証）` → gen-l3 が検証場所を確定して `（未確認・PH-xxxx で検証）` | gen-l3 が検証作業化、gen-code が昇格時に除去 |
| 検証手段 | AC 直下の `- 検証:` サブ行 | gen-code が検証方法を決定 |
| YAML frontmatter | 各テンプレートのキー定義どおり | validate_ids / gen-code / archive-l3 |
| ID | `PREFIX-nnnn`（4桁連番・永久欠番） | validate_ids・全スキル |

## 人間可読性との両立

生成ドキュメント内では XML タグによる強調は使わない（人間も読むため）。強い制約は L1「原則」セクション・太字・表で表現する。
（XML タグによる強指示はスキル定義側の技法 — `.claude/rules/skill-development.md` を参照）
