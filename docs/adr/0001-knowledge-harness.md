# ADR-0001 工程オーケストレーションから知識ハーネスへ再設計する

## 状況

v5 までの Tri-SSD は、L1（要件）→ L2（構成）→ L3（フェーズ）の文書を順に生成する 12 の Skill で開発工程を導いていた。
Claude Code による長期開発で、次の問題が顕在化した。

- 文書更新を任せると、変更前の状態が本文に残る（履歴汚染）
- 情報が削除・置換されず追記され、重複・矛盾・トークン消費が増える
- 作業に必要な範囲が分からず、関連の薄い文書まで読む
- 仕様と実装の差分を作業として管理できない
- セッションをまたいで発見が失われる、または不要な形で恒久文書に溜まる

工程の順序を強制する Skill 群は、エージェントの能力が上がるほど価値が下がり、上の問題には効かなかった。

## 決定

知識のライフサイクルとコンテキストを管理するハーネスに再設計する。

- 置き場を L0〜L3 の抽象度ではなく、更新契機と寿命で分ける: Goal・Docs・Tasks・Notes・CHANGELOG
- 決定的な処理を1つの CLI（`scripts/tri.py`、標準ライブラリのみ）に集約する: 知識グラフ・関連セクションの取得・逆引き・検査・完了ゲート・採番・ノート・移行
- Skill を 12 から 4 に減らす（setup・task・docs・note）。各 Skill は CLI の使い方と、エージェントにしかできない判断だけを書く
- 自動発火で保証できない2点だけをフックにする: セッション開始時の現在位置の注入、Docs 編集直後の検査

| v5 の要素 | 扱い | 理由 |
|---|---|---|
| L1/L2/L3 の固定階層 | Goal・Docs・Tasks に置換 | 抽象度では置き場が決まらない。更新契機と寿命で決める思想は継承 |
| フェーズ（PH）と機能（F） | 検証可能な Task に置換（ID は互換で有効） | フェーズ計画は完了で腐る。差分の解消単位の方が完了を証拠で判定できる |
| gen-l1/gen-l2/gen-interface/gen-data/gen-doc | docs スキル＋種類別ガイドに統合 | 生成工程の分割は同じ能力（Docs の作成・改訂）の重複だった |
| gen-l3/gen-code/archive-l3/reshape-l3 | task スキル＋CLI に統合 | 計画・実装・完了は1つの作業の流れ。フォルダ形式の往復変換は不要になった |
| next-tri-ssd/review-tri-ssd | SessionStart フック・`status`・`check`・`gaps` に置換 | 現在地の判定と検査は決定的処理 |
| doc_graph.py・validate_ids.py・next_id.py | `project.py`・`resolve.py`・`check.py` に統合・拡張 | ID 参照に加え、リンク・見出し・コードパスを使うセクション単位のグラフが必要 |
| 「確認済みの前提」「設計判断の記録」節 | Docs の本文と ADR に分離 | 判断の経緯を本文に置くと履歴汚染の温床になる |

## 結果

- 文書の改訂は「置き換え＋CHANGELOG」になり、履歴汚染・重複・肥大化は検査で機械的に検出される
- 作業ごとに必要なセクションだけを、理由と予算付きで取得できる
- Task の完了は受け入れ条件ごとの証跡と作業ツリーの指紋で判定される
- 依存が書かれていない関係（横断的な制約・エンティティ定義）はグラフで辿れない。語彙の一致で候補を示し、見つけた関係を書き足す運用で補う
