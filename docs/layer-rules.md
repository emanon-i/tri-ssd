# レイヤー配置ルール（Layer Rules）

Tri-SSD で「どの情報を・どのレイヤーの・どのファイルに置くか」を判定するための正規ルール。
このファイルが配置判断の唯一の出所（SSOT）。他のドキュメント・スキルは本ファイルを参照する。

## レイヤー責務

| 層 | 一言責務 | 更新トリガー | 場所 |
|---|---|---|---|
| L0 | 要求の**原石**（未加工の入力。任意） | 発想が変わる | docs/l0_ideas/ |
| L1 | **なぜ・何を**（要求と成功条件の正） | 要求が変わる | docs/l1_requirements/vision.md |
| L2 | **どう作られているか**（現在の設計と確認済み前提の正） | 技術判断・外部環境が変わる | docs/l2_foundation/foundation.md |
| L3 | **今どう作るか・どう確かめたか**（完了で腐る計画と証跡） | 実装が進む | docs/l3_phases/PH-nnnn_*.md |

思想: **仕様は腐る、コードが真実**。L3 は完了後に陳腐化する前提で設計し、アーカイブで葬る。
L2 は「現在の実装＋これから実装する設計」だけを現在形で保ち、時系列の文脈は CHANGELOG が受け持つ。

ID形式: `PREFIX-nnnn`（REQ, PH, F）。番号はプロジェクト全体で通し（F を PH 内で振り直さない）。
一度使った番号は再利用しない（永久欠番。番号が巻き戻ると他レイヤーからの参照が別対象を指すサイレント破壊が起きるため）。
未確定箇所のマーク: 全レイヤー共通で `<!-- TODO: 要確認 -->` を使う（gen-code が実装前に検出して確認する。別形式で書くと検出されない）。

## 配置判定フロー

新しい情報が出たら上から順に判定（最初に Yes が出た層が置き場所）:

```
Q0. AI が管理しない生の発想・外部資料・壁打ちログか？
    → Yes: L0（無ければ捨ててもよい）
Q1. 実現手段を1つも決めなくても真か？
   （「誰が・何を・どこまでできれば成功か」の話か？）
    → Yes: L1
Q2. フェーズが完了しても真であり続けるか？
   （「今このプロダクトはどう作られているか」の話か？）
    → Yes: L2
Q3. 特定フェーズの計画・作業・証跡か？（完了したら腐るか？）
    → Yes: L3
Q4. どれでもない
    → 時系列の記録なら CHANGELOG／それ以外は更新トリガーが最も近い層へ
```

2層以上に該当しうるときの優先順位ラダー（上から順に適用して一意に決める）:
①更新トリガー（何が変わるとこの情報も変わるか）→ ②主な参照経路（どの工程が読むか）→
③変動性（変わりやすい方を下の層へ）→ ④archive ライフサイクル（フェーズと共に葬られるなら L3）

## 配置決定表

| 情報の種類 | 置き場所 | 根拠（更新トリガー） |
|---|---|---|
| 生アイディア・外部メモ・AI壁打ちログ | L0 | 発想が変わる。AIは整理以外更新しない |
| 背景・動機（なぜ作るか） | L1 | 問題認識が変わる |
| 機能要件・非機能要件（REQ） | L1 | 要求が変わる |
| 原則（プロジェクト全体の判断基準。任意） | L1 | 価値観が変わる（ほぼ不変） |
| 体験要件＝導線・状態・使い勝手の**要求**（GUI導線 / CLIのUX / APIのDX / 文書の読者体験） | L1 | 「誰がどう使えたら成功か」＝要求が変わる |
| スコープ外・やらないことの決定 | L1 | 要求スコープの判断が変わる |
| 技術選定（スタック・ライブラリ）＋選定理由 | L2 | 技術判断が変わる |
| システム構成・アーキテクチャ | L2 | 技術判断が変わる |
| データモデル＝概念モデル（主要エンティティ・関係・キー） | L2（分離時 data.md） | データ設計の判断が変わる |
| データライフサイクル（発生・増加ペース・ローテーション・保持/削除） | L2（分離時 data.md） | データ運用の判断が変わる |
| エラー処理方針（分類・見せ方・リトライ/ログ） | L2 | 技術判断が変わる |
| 設計判断の記録（判断・理由・却下案） | L2 | 技術判断が変わる |
| インターフェース仕様＝**具体**の画面構成 / CLIコマンド体系 / APIエンドポイント / 公開API / 入出力契約 / 文書の章立て | L2（分離時 interface.md） | 設計が変わる |
| 事前確認（スパイク）で**判明した事実**（外部API仕様・実測値・制約） | L2「確認済みの前提」節 | 外部環境が変わる。実装後も真であり続ける |
| 用語集 | L2 | ドメイン理解が変わる |
| テスト・検証**戦略**（何をどう検証する方針か） | L2 | 技術判断が変わる |
| 運用手順・環境変数・監視（継続運用するプロダクトのみ） | L2 | インフラ判断が変わる |
| 実装Plan（フェーズ・機能分割・着手順） | L3 | 進め方が変わる。完了で腐る |
| 受け入れ条件（AC）と検証手段 | L3 | 機能の完了定義が変わる（REQ は ID 参照） |
| 事前確認の**作業**（何を確かめるかのタスク） | L3「事前確認」節 | Plan が変わる。実施済みで腐る |
| 検証**結果**（PASS/PARTIAL・実行日・証跡） | L3「検証記録」節 | 実装が進む。事後証跡のみ |
| 進捗ステータス | L3 frontmatter `status` | 実装が進む |
| 完了サマリ・実装で得た知見 | L3「完了サマリ」節（archive 時に L1/L2/CHANGELOG へ還元） | フェーズ完了 |
| 変更履歴 | CHANGELOG.md（レイヤー外・L3 完了サマリの派生） | フェーズ完了/archive |

## 曖昧ケースの裁定

| 迷いやすいペア | 裁定 |
|---|---|
| 要件 vs 設計 | 「〜できること」（手段独立）→ L1／「〜で実現する」→ L2。「速い」は要求、「Redis でキャッシュ」は設計 |
| 設計判断の理由 vs 要件の意思決定 | 判断の主語が要求スコープ（やる/やらない）→ L1／技術・構成（何で/どう作る）→ L2 |
| 事前確認の結果 vs 設計 | 判明した外部の事実 → L2「確認済みの前提」節／その事実を受けた自分の判断 → L2「設計判断の記録」節（同じ L2 でも更新トリガーが違うので節を分ける） |
| 事前確認の結果 vs 検証結果 | 実装**前**に世界について知ったこと → L2／実装**後**に自分のコードについて確かめたこと → L3「検証記録」節 |
| Plan vs 検証結果 | 同一 PH ファイル内で節分離（「機能」節 / 「検証記録」節）。参照単位が同じなのでファイルは分けない |
| 体験の要求 vs インターフェース仕様 | 「3ステップ以内で購入できる」→ L1／「詳細画面に購入ボタンを右上配置」→ L2 |
| 冪等性・再実行可能性 | 「失敗時に再実行できること」（要求）→ L1／冪等化の実装方式 → L2 |
| バグ・不具合の記録 | 修正作業 → L3（現行 PH または新 PH の F）／原因が設計前提の誤りなら L2 の前提・設計判断を**同時に更新**。経緯は L3 完了サマリ → CHANGELOG |
| スキーマ定義 vs データ設計 | カラム定義・型・インデックスの正は**実装コード**（migration/DDL/ORM）。L2（data.md）に書くのは概念モデル・ライフサイクル・整合性の判断基準＋正へのパス参照。全カラム表の複製は SSOT 違反 |
| 未確認の仮定 vs 確認済みの前提 | 未確認の仮定 → L2「設計判断の記録」に `（未確認・要検証）` 印付きで置く（gen-l3 が検証場所を確定し `（未確認・PH-xxxx で検証）` に更新）／検証**作業** → L3（計画全体を左右するなら PH-0000 のスパイク F、特定フェーズのみなら該当 PH の「事前確認」）／検証で判明した**事実** → L2「確認済みの前提」へ昇格し印を外す |

## ファイル分割ルール

**大原則: デフォルトは統合**。分割は以下のトリガーのうち **2つ以上に該当**するか、⑤に単独該当したときのみ。

| # | 分割トリガー | 例 |
|---|---|---|
| ① | 更新タイミングが異なる | L3 を PH ごとにファイル化 |
| ② | 参照単位が異なる（ある工程が一部だけ読む＝段階的注入の単位が違う） | gen-code は対象 PH だけ読む |
| ③ | 独立して archive される | PH ファイル |
| ④ | 関心領域が明確に独立し、読者も異なる | 用語集が肥大した場合のみ glossary.md |
| ⑤ | サイズ超過で必要部分だけ読めない（目安: 1ファイル300行超） | foundation.md 超過時に interface.md を分離 |

適用結果:
- **L1** = `vision.md` 1ファイル維持（原則・体験要件も同居。全 REQ の一覧性が価値）
- **L2** = `foundation.md` をハブとする複数ファイル構成。既定は foundation 内セクションだが、関心領域が独立し（④）参照単位も異なる（②: gen-code は UI 実装時だけ画面仕様を読む）＝2トリガー該当のため、それが実際に効き始める規模（以下の目安は大原則の運用値）で分離する:
  - `interface.md`（画面一覧・遷移図・導線）: 画面5枚超 or 主要導線3本超 or §3 が約100行超 → gen-interface
  - `data.md`（概念モデル・データライフサイクル）: エンティティ7個超 or ライフサイクル要件（ローテーション・保持期限）あり or §2.4 が約100行超 → gen-data
  - `glossary.md`（用語集）: ⑤該当時のみ
  - いずれも foundation.md 300行超（⑤）でも分離する。分離時は foundation の該当セクションを1行ポインタに置換（索引は複製可）
- **L3** = PH ごと1ファイル（①②③該当）。PH 内の Plan/検証記録は節分離のみ。大型 PH は F 単位分割（reshape-l3）

## 適正粒度の基準

| 単位 | 適正粒度 | 細かすぎシグナル | 粗すぎシグナル |
|---|---|---|---|
| REQ | 検証可能な要求文1つ。1プロダクト 5〜20個 | 実装手段を書いている | 「使いやすい」等検証不能 |
| PH | デモ可能な縦切り。F 3〜7個、1〜2セッションで完了 | F 1個だけの PH が連続 | 1 PH が複数の独立デモに割れる |
| F | AC 2〜5個、数コミット規模 | AC 1個の F が多数 | 複数 REQ にまたがる |
| AC | 観測可能な振る舞い1つ＋`検証:` 1行 | 実装詳細の羅列 | 検証手段が書けない |
