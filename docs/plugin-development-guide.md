# Claude Code プラグイン開発 原則・推奨事項ガイド

このドキュメントは、Tri-SSD Claude Code プラグイン開発における原則と推奨事項を定義します。
スキル定義の必須規約は `.claude/rules/skill-development.md`（skills/ 編集時に自動注入）が正です。本ガイドはその背景と設計パターンを補足します。

---

## 1. 基本原則

### 1.1 ファイルサイズと段階的開示

| 対象 | 推奨 | 上限 | 理由 |
|------|------|------|------|
| SKILL.md 本文 | 200-300行 | 500行未満 | 発火時に全文がロードされるため |
| 参照ファイル（references/） | - | 1階層まで | 多段参照は部分読みで情報を見落とす |
| CLAUDE.md | 150-200指示 | 300指示 | 常時ロードされ認知負荷になる |

**大きくなりすぎた場合の逃がし先（優先順）:**

1. 定型テンプレート・長い出力例 → `skills/<name>/references/`（必要時のみ読む）
2. 決定的処理（採番・変換・移動・検証） → `scripts/*.py`（実行のみ、コードはコンテキストに乗らない）
3. スキル横断の規約 → `docs/layer-rules.md` 等の共有ドキュメント（参照で繋ぐ）

### 1.2 単一責任原則

```
1スキル = 1つの明確な能力
```

**良い例:**
- `gen-l1` - L1要件ドキュメントの生成
- `reshape-l3` - L3の形式変換（split⇔merge は往復対の1能力）

**避けるべき例:**
- `trissd-all` - 全レイヤーを一度に生成（責任が広すぎる）

**例外**: 更新トリガーが同一の処理は1スキルにまとめてよい
（例: `archive-l3` のゲート確認・CHANGELOG追記・知見還元は、すべて「フェーズ完了」という同一イベントで発生する）。

### 1.3 SSOT（Single Source of Truth）

- 同じ規約・テンプレート・ロジックを複数スキルに複製しない
- レイヤー配置の判断規約 → `docs/layer-rules.md` が正
- ID採番・整合性検証 → プラグインルート `scripts/` が正（各スキルからは `${CLAUDE_SKILL_DIR}/../../scripts/` で参照）
  - パス変数は `${CLAUDE_SKILL_DIR}` を使う（skills 公式の置換変数。プラグインは全体がキャッシュへコピーされるため内部の相対参照は壊れない）
  - `${CLAUDE_PLUGIN_ROOT}` は使わない（スキル本文での展開が公式に保証されていない）
- 索引・ナビ・リンクは複製してよい（正規の事実そのものは複製しない）

## 2. スキル設計パターン

### 2.1 推奨構造

必須セクションは `.claude/rules/skill-development.md` の3つ（出力フォーマット定義・ID採番・完了後の案内）。標準的なスキルは以下の構造を持つ（引数なしのスキルは「引数」節に「引数なし」と書く）:

```markdown
---
description: 何をするか（三人称・1〜2文）
when_to_use: いつ使うか。「〜したい」等の自然な発火フレーズを列挙
argument-hint: "[引数] - 説明"
allowed-tools: Read, Write, Edit, Glob, Grep
---

# スキル名

<tri_ssd_context>
（共通コンテキストブロック。skill-development.md 参照）
</tri_ssd_context>

<avoid_over_engineering>
（過剰設計回避の指示）
</avoid_over_engineering>

## 概要
## 引数
## 手順
## 出力フォーマット
## 完了後の案内
## エラーケース
```

### 2.2 フロントマターの注意点

- `description` + `when_to_use` は合計**1,536文字以内**（超過分はトランケートされ発火精度が落ちる）
- `allowed-tools` は「制限」ではなく「事前承認」。確実に使うツールのみ列挙
- スキル呼び出し名は**ディレクトリ名**で決まる（`name` は原則書かない）

### 2.3 スクリプト同梱の作法

- 決定的処理（採番・変換・移動・検証）はスクリプト化する。コードはコンテキストに乗らず、出力のみトークンを消費する
- エラーハンドリングはスクリプト側で明示的に行う（Claude に丸投げしない）
- 冪等性を保証する（再実行しても安全）
- 改行は LF 固定で出力する（OS 非依存）
- 実行と参照を書き分ける（「`next_id.py` を実行」と「アルゴリズムは `next_id.py` を参照」は別）
- `python3` が無い環境では `python` / `py` にフォールバック

## 3. Tri-SSD 三層モデルとの整合性

### 3.1 レイヤースキップの禁止

```
L1 → L2 → L3 の順序を必ず守る
```

| 禁止パターン | 理由 |
|-------------|------|
| L1なしでL2を生成 | ビジョンなき技術設計 |
| L2なしでL3を生成 | 基盤なき機能仕様 |

### 3.2 配置判断

生成物のセクション設計・情報の置き場所は `docs/layer-rules.md` の配置決定表・判定フローに従う。
スキル本文にレイヤー詳細を複製しない。

### 3.3 ID形式の遵守

- `PREFIX-nnnn`（REQ, PH, F）
- 採番は `${CLAUDE_SKILL_DIR}/../../scripts/next_id.py` を実行（自前実装しない）
- 一度使った番号は再利用しない（永久欠番。`_archive/` 内の ID も走査対象）

## 4. エラー処理とフィードバック

### 4.1 エラーメッセージ

**良い例:**
```
❌ L2ドキュメントが見つかりません。
   先に /gen-l2 を実行してください。
```

**避けるべき例:**
```
エラーが発生しました。
```

### 4.2 進捗フィードバック

処理中は以下を報告: 現在のステップ / 完了した項目 / 次のアクション

## 5. チェックリスト

### スキル作成・変更時

- [ ] `description` + `when_to_use` があり、合計1,536文字以内
- [ ] `<tri_ssd_context>`（4行版）と `<avoid_over_engineering>` ブロックがある
- [ ] 出力フォーマットが明確に定義されている
- [ ] 完了後の案内がある
- [ ] 本文が500行未満
- [ ] レイヤー規約・採番ロジックを複製していない（layer-rules.md / scripts/ を参照している）

### リリース前

- [ ] 全スキルが単一責任を持つ
- [ ] エラーメッセージが明確
- [ ] ドキュメントが最新
- [ ] `CHANGELOG.md` / `plugin.json` / `marketplace.json` のバージョンが同期している
