# 文書の種類別ガイド

新しい Goal・Docs を作るときだけ読む。配置の判断は knowledge-model.md、書き方の規約は writing-rules.md が正。

## Goal（docs/goal.md）

```markdown
# <プロジェクト名> Goal

## 目的
誰のどんな問題を解決するか（2〜3 文）

## 成功状態
- 観測できる成功の条件（数値で書けるものは数値で）

## 原則
- 迷ったときの判断基準（任意・1〜3 個）

## やらないこと
- スコープ外と決めたこと（任意）
```

## 要求（例: docs/requirements.md）

- 見出しに ID を入れる: `## REQ-nnnn 名前`（番号は `tri id REQ`）
- 手段に依存しない「〜できる」と、検証可能な条件（数値・範囲）を書く
- 背景が要るのは判断が分かれた要求だけ。却下案の詳細は ADR へ

## 構成（例: docs/architecture.md）

- frontmatter `code:` に記述対象のコード範囲を書く（例: `code: [src/]`）
- 構成図（Mermaid flowchart）と、コンポーネント・責務・実装パスの表
- 技術選定は「何を使うか」と理由1行。経緯は ADR
- エラー処理方針・テスト戦略など、コード全体に効く制約は独立した見出しにする（context が見出し単位で取得する）

## 契約（API・CLI・画面・機能）

- 対象コードを frontmatter `code:` に書き、実装箇所を本文でパス名指しする
- 1 エンドポイント・1 コマンド・1 画面 = 1 見出し。関連する REQ を本文で ID 参照する
- 機能の「やらないこと」は契約として書く（実装時に逸脱を防ぐ）

## データ

- 概念モデル（Mermaid erDiagram）・ライフサイクル（発生・増加ペース・保持・削除）・整合性の基準
- カラム定義・型・インデックスの正はコード。パスで参照し、表を複製しない

## ADR（docs/adr/nnnn-題名.md）

- frontmatter `kind: adr`。経緯を書くことが目的なので履歴汚染の検査対象外
- 状況・決定・結果。決定後は書き換えず、覆すときは新しい ADR を書く

## 手順書

- 繰り返す作業（リリース・データ移行・環境構築）の手順。番号付きリストで、各手順の確認方法を添える
- 同じ手順が何度も使われるなら Skill 化の候補として引き継ぎに書き留める
