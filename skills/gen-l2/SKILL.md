# L2 生成スキル

<tri_ssd_context>
Tri-SSD: L0(任意メモ docs/l0_ideas/) → L1(要件 docs/l1_requirements/vision.md) → L2(構成 docs/l2_foundation/foundation.md) → L3(フェーズ docs/l3_phases/PH-xxxx.md)。
ID形式: PREFIX-nnnn（REQ, PH, F）。番号は再利用しない（永久欠番）。
配置・分割・粒度の判断に迷ったら `${CLAUDE_SKILL_DIR}/../../docs/layer-rules.md` を読むこと。
</tri_ssd_context>

## 概要

L1（要件）から L2 システム構成（foundation.md）を生成する。
技術選定はユーザーと対話して決める。

**L2 に書くのは「フェーズが完了しても真であり続ける」現在の設計だけ**。実装の計画・進捗・検証結果は L3 へ。過去の設計は残さない（時系列は CHANGELOG が受け持つ）。

## 生成時の原則

<avoid_over_engineering>
- 直接要求されたか、明確に必要な技術選定のみ行う
- シンプルな技術スタックを優先する（複雑な構成は避ける）
- 要件の規模に見合った技術を選定する（個人プロジェクトにエンタープライズ構成は不要）
- 「将来必要になるかも」で技術を追加しない
- 省略可のセクションは無理に埋めない
</avoid_over_engineering>

## 引数

- 引数なし（L1 から対話的に技術選定する）

### 使用例

```
/gen-l2
```

2. `docs/l2_foundation/foundation.md` が存在するか確認（再生成モード判定）

### 必須構造

**生成前に `${CLAUDE_SKILL_DIR}/references/foundation-template.md` を必ず読む**。テンプレート全文（§1 技術スタック〜§9 運用）と、各セクションの記入基準（データモデル・エラー処理方針・運用を書くかどうかの判断基準、Mermaid 記入例）が定義されている。

**必須**: フロントマター、セクション 1, 2 (2.1-2.3), 8
**省略可能**: セクション 2.4（データモデル）, 2.5（エラー処理方針）, 3, 4, 6, 7, 9（運用）— 記入基準に該当する場合のみ書く。5 は推奨

文体・構造化・図・機械契約マーカーの書式は `${CLAUDE_SKILL_DIR}/../../docs/writing-rules.md`（記載規約の SSOT）に従う。

### セクションの使い分け（重要）

- **「確認済みの前提」と「設計判断の記録」は混ぜない**。前者は外部の事実（外部環境が変われば更新）、後者は自分の判断（技術判断が変われば更新）
- 事前確認の**作業計画**は L3 の「事前確認」節へ、実装後の**検証結果**は L3 の「検証記録」節へ。L2 に置くのは「判明した事実」だけ
- インターフェース仕様は L1 の体験要件（要求）を満たす**具体形**。要求そのものは L1 に置いたまま複製しない

## 再生成モード（既存ファイルがある場合）

既存の `foundation.md` がある場合は**再生成モード**で動作する。

### 保持するもの（上書きしない）

| セクション | 理由 |
|-----------|------|
| 確認済みの前提 | 事実は設計変更で消えない（外部環境が変わった場合のみ更新） |
| 設計判断の記録（過去分） | 却下理由は資産。判断が覆った場合は現在の判断に書き換え、当該行に日付を添える（CHANGELOG への反映は archive-l3 経由のみ） |
| ユーザーが追記したメモ | 手動編集を尊重 |

### 更新するもの

| セクション | 条件 |
|-----------|------|
| 技術スタック | L1変更または明示的な変更要求時 |
| アーキテクチャ / インターフェース仕様 | 技術スタック変更に伴う場合 |

### 再生成時の手順

1. 既存ファイルを読み込み、各セクションの内容を把握
2. L1との差分を分析
3. ユーザーに「何を更新するか」を確認
4. 保持セクションはそのまま、更新セクションのみ再生成
5. 技術選定を変更した場合: 無効になった `（未確認…）` 印付きの仮定を削除または新しい仮定に更新する（棚卸し）

## 生成手順

### Step 1: L1分析

- 要件・`product_type`・体験要件を把握
- 用語の抽出
- 非機能要件の抽出

### Step 2: 技術選定（対話型）

候補が自明でないカテゴリのみ、WebSearch で候補を3個ずつ**並列で**検索:
- フレームワーク（フロント/バック）
- データベース
- 認証方式（必要な場合）
- インフラ/デプロイ先

（product_type が cli / library / doc 等の場合はカテゴリを適宜読み替える）
（**ユーザーが既にスタックを指定している・チームの既定スタックがある場合は検索せず**、選定理由の確認のみ行う。変化の速い領域・未知の領域だけ検索する）

<thinking_process>
技術選定の判断時は、以下の形式で思考を整理してから結論を出す：

1. **要件の確認**: L1で求められている規模・性能・セキュリティレベル
2. **候補の評価**: 各候補の長所・短所をL1要件に照らして評価
3. **チーム適合性**: ユーザーの技術スタック経験を考慮
4. **判断**: 最もシンプルかつ要件を満たす選択肢を推奨
</thinking_process>

選択肢を提示し、ユーザーが選ぶ。
選定の結論と却下案は「設計判断の記録」に1行ずつ残す。
選定が**未確認の仮定**に依存する場合（外部 API の仕様・レート制限、ライブラリの制約、核心処理の実現可否など）は、その仮定を「設計判断の記録」に `（未確認・要検証）` 印付きで残す。検証場所を決めるのは gen-l3（印のライフサイクルは writing-rules の機械契約マーカー表が正）。

### Step 3: アーキテクチャ設計

#### アーキテクチャ3原則（規模を問わず意識する）

| 原則 | 目的 | 具体例 |
|------|------|--------|
| 依存性の逆転 | テスト容易性・外部依存の差し替え | DB/APIへの依存をインターフェース経由にする |
| 境界の明確化 | 並列開発・影響範囲の限定 | 機能/レイヤーごとにディレクトリを分離 |
| インターフェース安定性 | 要件変更時の影響最小化 | 内部実装の変更が外部に漏れない設計 |

#### 推奨アーキテクチャ

**Screaming Architecture + DI** をデフォルトとする:
- フォルダはドメイン単位（orders/, users/）で構成する
- 外部依存（DB, API等）はDIで注入し、テスト時に差し替え可能にする
- shared/ は横断的関心事（認証、ログ、DB接続）のみ。2ドメインで共有する程度なら各ドメインに複製する方が安全

※ 大規模（複数チーム）の場合: 各ドメインフォルダ内に ports/adapters を追加検討

L1の要件規模を踏まえ、ユーザーと相談してパターンを調整する。

#### 過剰分割の防止

<avoid_over_fragmentation>
**ファイル分割 — やらないこと**:
- 実装が1つしかないインターフェースを作らない（テスト差し替えが必要な外部依存のみ例外）
- 全操作を UseCase/Service クラスに通さない（単純CRUDはリポジトリ直接呼び出しで良い）
- レイヤーごとに DTO + マッパーを作らない（変換が不要ならドメインモデルを直接渡す）
- 10-20行程度のファイルを量産しない（1ファイルに複数の関連する型/関数をまとめて良い）

**関数化 — やらないこと**:
- 1-2箇所からしか呼ばれず外部公開もしない処理を関数に切り出さない（インラインで書く）
- 関数化の前に、その関数自体が肥大化していないか確認する（300行超の関数は設計を見直す）

**関数化して良い場合**:
- 3箇所以上から呼ばれる、または外部に公開する
- 現時点で1-2箇所でも、仕様上明確に今後呼び出し箇所が増えるとわかっている

**判断基準**:
- 新機能追加時のファイル数が機能の複雑度に比例しているか
- 単純なCRUD機能で5ファイル以上必要なら過剰分割の兆候
</avoid_over_fragmentation>

#### 設計後の確認観点

以下を満たすか確認し、満たさない場合は設計を調整する:
- 調査と実装を並列に進められる境界があるか
- 要件が変わったとき、影響が局所化されるか
- 各コンポーネントを単独でテストできるか
- 単純な機能追加で不必要に多くのファイルが必要にならないか

#### データモデル（§2.4）の規模判定

foundation-template.md の記入基準に該当すればインラインで書く。
**エンティティ7個超、ライフサイクル要件（ローテーション・保持期限・増加ペース管理）あり、または §2.4 が約100行超になりそうな場合は `/gen-data` での `data.md` 分離を提案**する。
分離が承認されたら §2.4 には**骨子のみ**（主要エンティティ名の列挙1〜3行）＋「詳細は `/gen-data` で `data.md` へ（未作成）」と書き、インラインで全量は書かない（二度手間の回避。正式なポインタ化は gen-data 実行時）。
既に `data.md` が分離済みなら §2.4 はポインタのまま維持し、インライン再生成しない（更新は gen-data で行う）。

### Step 4: インターフェース仕様（L1 に体験要件がある、または外部との契約がある場合）

foundation-template.md の §3 の product_type 別リストに沿って具体仕様をインラインで記述する:

- 各仕様が L1 のどの体験要件・REQ に応えるかを ID で対応付ける（本文は複製しない）
- 要求レベルの記述（「〜できること」）が混ざったら L1 へ戻す
- **画面5枚超・主要導線3本超・§3 が約100行超になりそうなら `/gen-interface` での `interface.md` 分離を提案**する（gui は「画面一覧・画面遷移図・主要導線」の3点セットで深掘りできる）
- 分離が承認されたら §3 には**骨子のみ**（主要画面名の列挙1〜3行）＋「詳細は `/gen-interface` で `interface.md` へ（未作成）」と書き、インラインで全量は書かない（正式なポインタ化は gen-interface 実行時）
- 既に `interface.md` が分離済みなら §3 はポインタのまま維持し、インライン再生成しない（更新は gen-interface で行う）

### Step 5: 非機能要求整理（必要な場合のみ）

L1の非機能要求を具体化: 性能（レスポンス時間等）/ セキュリティ（認証・認可方式）/ 可用性（SLA等）

### Step 6: テスト・検証戦略

選定した技術スタックに対応するテスト・検証ツールを整理:
- 技術スタックから自明なテストフレームワークを記載（例: React → jest/vitest）
- L1で性能要件やAPI仕様がある場合、検証ツールも記載（例: curl, k6）
- **L3の受け入れ条件でエージェントが自律検証するための基盤**となる
- **実装後の自己検証手段**を必ず定義する（コマンド + 期待結果のペア）
