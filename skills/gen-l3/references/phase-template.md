# フェーズファイル テンプレート＋記入ガイド

gen-l3 が L3（`docs/l3_phases/PH-xxxx_*.md`）を生成する際の正規テンプレート。
生成前にこのファイル全体を読み、記入基準に従うこと。
YAMLフロントマターの定義は SKILL.md 本文に従う（ここでは複製しない）。
準備フェーズ PH-0000 の内容ガイドは `ph-0000-template.md`（出力フォーマットは本テンプレと同一）。
PH / F / AC の適正粒度は layer-rules.md「適正粒度の基準」を参照。

## テンプレート全文（本文構造）

```markdown
# PH-xxxx: [フェーズ名]

## 目的

このフェーズで達成すること（1-2文）

## 事前確認（省略可）

実装前に確かめる作業のみを書く（結果の事実は L2「確認済みの前提」へ記入し、ここはチェックだけ残す）:

- [ ] [確認する作業] → 結果は L2 へ

## 機能一覧

### F-xxxx: [機能名]

**対応REQ**: REQ-xxxx

[機能の概要説明（2-3行）]

**受け入れ条件**:

- [ ] [条件1]
  - 検証: [検証手段]
- [ ] [条件2]
  - 検証: [検証手段]

---

### F-xxxx: [機能名]

**対応REQ**: REQ-xxxx

[機能の概要説明（2-3行）]

**受け入れ条件**:

- [ ] [条件1]
  - 検証: [検証手段]

---

## Exit Criteria

- [ ] [フェーズ完了の確認項目1]
- [ ] [フェーズ完了の確認項目2]

## 検証記録

（実装後に gen-code が記入する事後証跡。生成時は空のまま置く）

## 完了サマリ

（archive-l3 実行時に記入。生成時は空のまま置く）
```

（`- 検証:` 行は省略可。省略時はテストで確認がデフォルト。複数機能は `---` で区切る）

**必須**: 目的、機能一覧（受け入れ条件付き）、Exit Criteria
**省略可能**: 事前確認、複雑な機能のみ追加説明
**空のまま生成**: 検証記録、完了サマリ（見出しだけ置く。Plan と事後証跡を混ぜないため）

## セクション別記入ガイド

| セクション | 何を書く | 書かない / 判断基準 |
|---|---|---|
| 目的 | このフェーズで達成すること1-2文 | 機能の再列挙 |
| 事前確認 | 「この設計で実装できるか不確実」な場合のみ、確かめる作業 | 判明した事実（→ L2「確認済みの前提」へ） |
| 機能一覧（F） | 対応REQ・概要2-3行・AC 2〜5個 | 実装手順の詳細（コード生成時に AI が考える） |
| Exit Criteria | フェーズ完了の確認項目（全ACパス・結合テスト・デモ可能な状態） | AC の再掲 |
| 検証記録 | 見出しだけ置いて空のまま | 生成時に何かを書くこと（gen-code が記入する） |
| 完了サマリ | 見出しだけ置いて空のまま | 同上（archive-l3 が記入する） |

## 受け入れ条件（AC）の書き方

- ユーザー視点で「何ができればOKか」を、**コーディングエージェントが自律的に検証可能**な形で書く
- 1機能につき2〜5個程度（10個以上は過剰）
- 検証手段が明確な場合は `- 検証:` サブ行を追加（不明なら省略可）
- L2 に「テスト・検証戦略」があれば、そこのツール・コマンドを活用する

### 検証手段の種類

| 種類 | 記述例 | 使い分け |
|------|--------|----------|
| テスト | `検証: テスト test_create_item がパス` | 振る舞い検証（デフォルト） |
| コマンド | `検証: curl -s /api/health → 200` | API・CLI の検証 |
| 目視 | `検証: 目視確認` | **最終手段**。スナップショットテスト等で代替を検討 |

**原則: 目視確認は極力避ける。** UI でもスナップショットテスト、DOM アサーション、スクリーンショット比較等で自動検証できないか先に検討する。どうしても自動化不可能な場合のみ `目視確認` を使う。

### 良い例 / 悪い例

**良い例**:

- [ ] タイトル入力→作成→一覧に表示される
  - 検証: テスト `test_create_item_appears_in_list` がパス
- [ ] APIレスポンスが200ms以内
  - 検証: `curl -w '%{time_total}' /api/items` で確認
- [ ] 不正な CSV を指定すると非0 exit code と stderr に原因1行が出る
  - 検証: テスト `test_invalid_csv_exits_nonzero` がパス

**悪い例**:

- [ ] 適切に動作する ← 曖昧、検証手段なし
- [ ] エラーハンドリングが実装されている ← 何のエラー？検証不能（L2 §2.5 エラー処理方針を先に定義し、個別の振る舞いを AC 化する）
