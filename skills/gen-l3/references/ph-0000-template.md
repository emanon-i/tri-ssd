# PH-0000（準備フェーズ）の生成ガイド

初回実行時（gen-l3 の前提処理で**初回実行モード**と判定された場合）に、機能フェーズ（PH-0001〜）の前に自動生成する準備フェーズの定義。
L2（foundation.md）の「技術スタック」と「テスト・検証戦略」セクションを参照し、プロジェクトの技術に適したツールを選定して以下の6機能を生成する。出力フォーマットは通常のフェーズファイルと同一（`phase-template.md` 参照。frontmatter 含む）。

## F-xxxx: 開発環境の隔離

プロジェクト固有の環境をグローバル環境から分離する。

| L2の技術スタック | 推奨ツール |
|-----------------|-----------|
| Python | venv, pyproject.toml |
| Node.js | .nvmrc, package.json (engines) |
| 複数言語 | .tool-versions (mise/asdf), devcontainer |
| コンテナ前提 | Dockerfile, docker-compose.yml, devcontainer |

**受け入れ条件の方向性**:
- クローン後のセットアップ手順が1コマンドで完了する
- グローバル環境にパッケージがインストールされない
- セットアップ手順が README またはスクリプトに記載されている

## F-xxxx: 技術前提の事実検証（スパイク）

計画全体が依存する**未確認の前提**を、実装に入る前に最小の検証コード・実測で確認する。

**検証対象の抽出元**:
- L2「設計判断の記録」の `（未確認…）` 印（`（未確認・要検証）` / `（未確認・PH-0000 で検証）`）が付いた仮定
- L1「制約条件・前提」（§2）の外部システム連携
- L2 の技術選定の根幹に関わる仮定（これが崩れると計画を作り直すもの）

**検証対象の例**:
- 外部 API が想定どおり使えるか（エンドポイントの実在・認証方式・レート制限・応答形式）
- 核心処理（フィルタ・マスキング・変換等）が選定した技術スタックで想定どおり実現できるか
- 採用ライブラリの制約・ライセンスが要件と矛盾しないか

**受け入れ条件の方向性**:
- 各前提について最小の検証コードまたは実測で確認できている（検証コードは `spike/` 等の使い捨てディレクトリに置き、本実装に混ぜない。コミット可・後で削除可）
- 判明した事実が L2「確認済みの前提」に出所付きで記録され、「設計判断の記録」の `（未確認…）` 印が外れている
- 前提が崩れた場合: **不成立の確認も検証の成果**として検証記録に `PASS（前提不成立を確認、日付）` と記録し、実装に入らず L2 の技術選定・設計と以後のフェーズ計画の見直しをユーザーに提案している

**適用基準**: 未確認の前提が無ければこの機能ごと省略する。特定フェーズだけに影響する前提は PH-0000 でなく該当フェーズの「事前確認」節へ（振り分けは gen-l3 が行う）。

## F-xxxx: テスト基盤

テストランナーとテストコマンドを整備する。

- L2 の「テスト・検証戦略」に定義済みのテストフレームワーク・コマンドをセットアップ
- テストコマンドがゼロテスト状態で正常終了すること
- カバレッジ計測の設定（L2 で指定がある場合）

**受け入れ条件の方向性**:
- テストコマンドが正常に実行できる（テスト0件でもエラーにならない）
- CI環境でも同じコマンドでテスト実行可能
- テスト結果が機械可読な形式で出力される（JUnit XML等）

## F-xxxx: セルフ検証機構

Lint・型チェック・フォーマットチェックを設定する。

| L2の技術スタック | 推奨ツール |
|-----------------|-----------|
| TypeScript | eslint, prettier, tsc --noEmit |
| Python | ruff (lint+format), mypy/pyright |
| Go | golangci-lint, go vet |

**受け入れ条件の方向性**:
- Lint コマンドがエラー0件で通る
- 型チェックがエラー0件で通る
- pre-commit hook または lint-staged が設定されている

## F-xxxx: エージェント可読ログ

コーディングエージェントが解析し「何を直すべきか」を判断可能な構造化ログを設定する。

- JSON 形式またはキーバリュー形式のログ出力
- エラー時にスタックトレース・コンテキスト情報（リクエストID、入力値等）を含む
- ログレベル（debug/info/warn/error）の使い分けを設定

**受け入れ条件の方向性**:
- アプリケーションログが JSON 等の構造化形式で出力される
- エラーログにスタックトレースとリクエストコンテキストが含まれる
- ログレベルで出力をフィルタリングできる

## F-xxxx: ログローテーション

ログファイルの肥大化を防止する仕組みを整備する。

| ログ出力先 | アプローチ |
|-----------|-----------|
| ファイル出力 | logrotate 設定 or アプリ内ローテーション（サイズ/日次） |
| stdout/stderr | コンテナ/プラットフォームのログ管理に委任（方針をドキュメント化） |
| 外部サービス | 送信設定とリテンションポリシーの明記 |

**受け入れ条件の方向性**:
- ログローテーションの仕組みが設定されている、または管理方針がドキュメント化されている
- 古いログが自動で削除またはアーカイブされる設定がある

## 適用の注意

- product_type が doc（非コード成果物）の場合、PH-0000 は「執筆環境の整備」（リポジトリ構成・Lint（textlint等）・レビュー手順）に読み替えるか、ユーザーに確認のうえスキップしてよい
- 6機能すべてが必須ではない。プロジェクト規模に照らして不要な機能（例: ログローテーション、未確認前提が無ければスパイク）はユーザー確認のうえ省略する

## 生成のフロー

1. L2 の技術スタックを参照し、上記の機能（適用基準で省略したものを除く）の受け入れ条件を具体化する
2. `docs/l3_phases/PH-0000_preparation.md` にフェーズファイルを書き出す（frontmatter の `requires` は対応 REQ が無ければ空リスト `[]` でよい）
3. ユーザーに PH-0000 の生成を報告する
4. 続けて通常のフェーズ計画に進む（PH-0001〜）
