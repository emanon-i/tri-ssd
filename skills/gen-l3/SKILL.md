# L3 フェーズ生成コマンド

<tri_ssd_context>
Tri-SSD（Tri-Layer Slice Spec Driven）はAI/LLMコードエージェントを前提とした仕様駆動開発。

レイヤー構造:
- L0: アイディア・ラフメモ（docs/l0_ideas/）- 任意
- L1: 要件（docs/l1_requirements/vision.md）
- L2: システム構成（docs/l2_foundation/foundation.md）
- L3: フェーズ（docs/l3_phases/PH-xxx.md）- 機能+受け入れ条件

ID形式: PREFIX-nnnn（REQ, PH, F）
</tri_ssd_context>

## 概要

L1/L2 をベースに、L3 フェーズドキュメントを生成する。
各フェーズは独立したファイルとして `docs/l3_phases/` に配置。

**フェーズ = 実装単位**。機能と受け入れ条件をインラインで記述。

## 生成時の原則

<avoid_over_engineering>
- **フェーズを細かく分けすぎない**: 2〜4フェーズ程度が適切
- 各フェーズは「デモ可能な成果物」を出せる単位にする
- 受け入れ条件は1機能につき2〜5個程度（10個以上は過剰）
- 最初のフェーズは小さく、早く成果を出せる構成にする
- 詳細はコード生成時にAIが考える（ここでは概要レベル）
</avoid_over_engineering>

## 引数

- `$ARGUMENTS` (省略可): 対象フェーズID
  - **省略**: 全体計画（複数フェーズを提案）
  - **PH-xxx**: 特定フェーズのみ生成・更新

### 使用例

```
/gen-l3                           # 全体計画（2〜4フェーズ提案）
/gen-l3 PH-0001                   # 特定フェーズを再生成
```

## 前提処理

1. `docs/l1_requirements/vision.md` を読み込み、要件を把握する
2. `docs/l2_foundation/foundation.md` を読み込み、技術スタックを把握する
3. `docs/l3_phases/` 内の既存フェーズを確認（再生成モード判定）
4. **初回実行判定**: Glob `docs/l3_phases/PH-*.md`（`_archive/` 除外）が0件なら → 初回実行モード（PH-0000 自動生成）

## 初回実行: 準備フェーズ (PH-0000)

`docs/l3_phases/` 内に PH-*.md が存在しない場合、以下の準備フェーズを**機能フェーズ（PH-0001〜）の前に自動生成**する。

### 判定条件

- Glob `docs/l3_phases/PH-*.md` の結果が0件（`_archive/` 配下は除外）
- 引数で特定 PH-ID を指定されていても、ディレクトリが空なら PH-0000 を先に生成する

### PH-0000 の構成

L2（foundation.md）のセクション1（技術スタック）とセクション5（テスト・検証戦略）を参照し、プロジェクトの技術に適したツールを選定して以下の5機能を生成する。出力フォーマットは通常のフェーズファイルと同一。

#### F-xxxx: 開発環境の隔離

プロジェクト固有の環境をグローバル環境から分離する。

| L2の技術スタック | 推奨ツール |
|-----------------|-----------|
| Python | venv, pyproject.toml |
| Node.js | .nvmrc, package.json (engines) |
| 複数言語 | .tool-versions (mise/asdf), devcontainer |
| コンテナ前提 | Dockerfile, docker-compose.yml, devcontainer |

**受け入れ条件の方向性**:
- クローン後のセットアップ手順が1コマンドで完了する
- グローバル環境にパッケージがインストールされない
- セットアップ手順が README またはスクリプトに記載されている

#### F-xxxx: テスト基盤

テストランナーとテストコマンドを整備する。

- L2 のセクション5に定義済みのテストフレームワーク・コマンドをセットアップ
- テストコマンドがゼロテスト状態で正常終了すること
- カバレッジ計測の設定（L2 で指定がある場合）

**受け入れ条件の方向性**:
- テストコマンドが正常に実行できる（テスト0件でもエラーにならない）
- CI環境でも同じコマンドでテスト実行可能
- テスト結果が機械可読な形式で出力される（JUnit XML等）

#### F-xxxx: セルフ検証機構

Lint・型チェック・フォーマットチェックを設定する。

| L2の技術スタック | 推奨ツール |
|-----------------|-----------|
| TypeScript | eslint, prettier, tsc --noEmit |
| Python | ruff (lint+format), mypy/pyright |
| Go | golangci-lint, go vet |

**受け入れ条件の方向性**:
- Lint コマンドがエラー0件で通る
- 型チェックがエラー0件で通る
- pre-commit hook または lint-staged が設定されている

#### F-xxxx: エージェント可読ログ

コーディングエージェントが解析し「何を直すべきか」を判断可能な構造化ログを設定する。

- JSON 形式またはキーバリュー形式のログ出力
- エラー時にスタックトレース・コンテキスト情報（リクエストID、入力値等）を含む
- ログレベル（debug/info/warn/error）の使い分けを設定

**受け入れ条件の方向性**:
- アプリケーションログが JSON 等の構造化形式で出力される
- エラーログにスタックトレースとリクエストコンテキストが含まれる
- ログレベルで出力をフィルタリングできる

#### F-xxxx: ログローテーション

ログファイルの肥大化を防止する仕組みを整備する。

| ログ出力先 | アプローチ |
|-----------|-----------|
| ファイル出力 | logrotate 設定 or アプリ内ローテーション（サイズ/日次） |
| stdout/stderr | コンテナ/プラットフォームのログ管理に委任（方針をドキュメント化） |
| 外部サービス | 送信設定とリテンションポリシーの明記 |

**受け入れ条件の方向性**:
- ログローテーションの仕組みが設定されている、または管理方針がドキュメント化されている
- 古いログが自動で削除またはアーカイブされる設定がある

### PH-0000 生成のフロー

1. L2 の技術スタックを参照し、上記5機能の受け入れ条件を具体化する
2. `docs/l3_phases/PH-0000_preparation.md` にフェーズファイルを書き出す
3. ユーザーに PH-0000 の生成を報告する
4. 続けて通常のフェーズ計画（Step 1〜5）に進む（PH-0001〜）

## 再生成モード（既存ファイルがある場合）

既存のフェーズファイルがある場合は**再生成モード**で動作する。

### 保持するもの（上書きしない）

| セクション | 理由 |
|-----------|------|
| 受け入れ条件のチェック状態 | 進捗を保持（`[x]` を消さない） |
| Exit Criteria のチェック状態 | 進捗を保持 |
| 実装メモ（あれば） | 知見を保持 |
| アーカイブ済みファイル | `_archive/` 内のファイルは対象外 |

### 更新するもの

| セクション | 条件 |
|-----------|------|
| 機能の概要 | L1要件が変更された場合 |
| 受け入れ条件（未チェック分） | 要件変更時 |
| 新規機能の追加 | L1に新しいREQが追加された場合 |

### 再生成時の手順

1. 既存ファイルを読み込み、チェック状態を把握
2. L1/L2との差分を分析
3. ユーザーに「何を更新するか」を確認
4. 完了済み項目は保持、未着手部分のみ更新

## 生成手順

### Step 1: 全体フェーズ計画（引数なしの場合）

1. L1の要件を機能候補に分解
2. 機能を「結合して意味のある単位」でグルーピング
3. フェーズ数を決定（2〜4フェーズ推奨）
4. ユーザーにフェーズ計画を提示して確認

<thinking_process>
フェーズ設計前に、以下を判断する：

1. **適切なフェーズ数は？**
   - 小規模（機能5個以下）: 2フェーズ
   - 中規模（機能6〜15個）: 3フェーズ
   - 大規模（機能16個以上）: 4フェーズ

2. **各フェーズの境界は？**
   - 「この時点でユーザーに見せられるか？」で判断
   - 技術的な区切りより、ビジネス価値の区切りを優先

3. **最初のフェーズに何を入れるか？**
   - 早く成果を出せる機能を優先
   - 依存関係の根幹となる機能を含める
</thinking_process>

### Step 2: 機能分解とID採番

- L1の各REQを機能に分解
- 機能IDは F-nnnn 形式で採番
- 各機能に対応REQを紐付け

### Step 3: 受け入れ条件の記述

各機能に対して:
- ユーザー視点で「何ができればOKか」を記述
- 1機能につき2〜5個程度
- **コーディングエージェントが自律的に検証可能**な形で書く
- **検証手段が明確な場合は `- 検証:` サブ行を追加**（不明な場合は省略可）
- L2のセクション5（テスト・検証戦略）が存在する場合、そこのツール・コマンドを活用

**検証手段の種類**:

| 種類 | 記述例 | 使い分け |
|------|--------|----------|
| テスト | `検証: テスト test_create_item がパス` | 振る舞い検証（デフォルト） |
| コマンド | `検証: curl -s /api/health → 200` | API・CLIの検証 |
| 目視 | `検証: 目視確認` | **最終手段**。スナップショットテスト等で代替を検討 |

**原則: 目視確認は極力避ける。** UIでもスナップショットテスト、DOMアサーション、スクリーンショット比較等で自動検証できないか先に検討する。どうしても自動化不可能な場合のみ `目視確認` を使う。

**良い例**:
- [ ] タイトル入力→作成→一覧に表示される
  - 検証: テスト `test_create_item_appears_in_list` がパス
- [ ] タイトル空で送信→エラーメッセージ表示
  - 検証: テスト `test_create_item_empty_title_error` がパス
- [ ] APIレスポンスが200ms以内
  - 検証: `curl -w '%{time_total}' /api/items` で確認
- [ ] ページネーションが表示される
  - 検証: テスト `test_pagination_renders_correctly`（DOM要素の存在確認）

**悪い例**:
- [ ] 適切に動作する ← 曖昧、検証手段なし
- [ ] エラーハンドリングが実装されている ← 何のエラー？検証不能
- [ ] 画面がいい感じに見える ← 目視確認に逃げている。レイアウトテストで代替可

### Step 4: Exit Criteria の設定

各フェーズの完了条件を設定:
- 全機能の受け入れ条件がパスしている
- 結合テストがパスしている（必要な場合）
- デモ可能な状態になっている

### Step 5: ファイル生成

フェーズごとに独立ファイルを生成:
```
docs/l3_phases/
├── PH-0000_preparation.md    ← 初回実行時に自動生成
├── PH-0001_mvp.md
├── PH-0002_beta.md
└── PH-0003_release.md
```

## ID採番ロジック

ID は同梱スクリプトで採番する（採番ミス防止）:

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/next_id.py" PH             # 次のフェーズID
python3 "${CLAUDE_SKILL_DIR}/scripts/next_id.py" F --count 5    # 機能IDを連続5件
```

`python3` が無ければ `python` / `py`。スクリプトが使えない場合は手動で（既存ID を Grep で検索 → 最大 + 1 → 4桁ゼロ埋め）。

### フェーズID（PH）
- **PH-0000** は準備フェーズとして予約（初回実行時に自動生成）
- 機能フェーズは **PH-0001** から開始（既存 PH が無ければ `next_id.py PH` は自動的に PH-0001 を返す）

### 機能ID（F）
- `next_id.py F --count N` でまとめて採番

## 出力ファイル

| ファイル |
|---------|
| `docs/l3_phases/PH-nnnn_[phase-name].md` |

ファイル名: `{フェーズID}_{kebab-case-フェーズ名}.md`
例: `PH-0001_mvp.md`

## 完了後の案内

- 生成ファイルのパスを報告
- フェーズ数と機能数を報告
- **PH-0000 を生成した場合**: 準備フェーズが含まれる旨を明記し、`/gen-code PH-0000` で環境整備から着手することを案内
- `/gen-code PH-xxx` または `/gen-code F-xxx` でコード生成できることを案内
- 実装完了後は `/archive-l3` でアーカイブできることを案内

## エラーケース

| ケース | 対応 |
|--------|------|
| L1が存在しない | エラー: 「L1が見つかりません。`/gen-l1` を先に実行してください」 |
| L2が存在しない | エラー: 「L2が見つかりません。`/gen-l2` を先に実行してください」 |
| L1/L2が作成途中 | 警告: 「L1/L2が作成途中の可能性があります。続行しますか？」 |
| 指定したPH-IDが存在しない | エラー: 「指定されたフェーズが見つかりません」 |
