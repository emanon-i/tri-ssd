# データ設計スキル

<tri_ssd_context>
Tri-SSD: L0(任意メモ docs/l0_ideas/) → L1(要件 docs/l1_requirements/vision.md) → L2(構成 docs/l2_foundation/foundation.md) → L3(フェーズ docs/l3_phases/PH-xxxx.md)。
ID形式: PREFIX-nnnn（REQ, PH, F）。番号は再利用しない（永久欠番）。
配置・分割・粒度の判断に迷ったら `${CLAUDE_SKILL_DIR}/../../docs/layer-rules.md` を読むこと。
</tri_ssd_context>

## 概要

L2 のデータ設計を深掘りし、`docs/l2_foundation/data.md` として foundation.md から分離・管理する。
foundation.md §2.4 のインライン記述では足りなくなった規模（エンティティ7個超・ライフサイクル要件（ローテーション・保持期限・増加ペース管理）あり・§2.4 が約100行超）で使う。

**書くのは「実装の判断基準」だけ**: 概念モデル・データライフサイクル・整合性の判断基準。
**スキーマのカラム定義の正は実装コード（migration/DDL/ORM）** — data.md からはそのパスを参照し、全カラム表を複製しない（SSOT）。
更新トリガーは foundation.md と同じ「設計判断が変わる」（L2 の一部。フェーズ完了後も真であり続ける）。

## 設計時の原則

<avoid_over_engineering>
- カラム定義・型・インデックスの網羅をしない（正は実装コード。ここは判断基準のみ）
- エンティティは L1 の要求に現れるものだけ（「将来必要かも」で増やさない）
- ライフサイクルは「増え続けるデータ」「消す必要があるデータ」にだけ書く（マスタ数件に保持ポリシーは不要）
- 正規化の教科書的完遂を目的にしない（要件が求める整合性だけ担保する）
- 図はすべて Mermaid（ASCII アートを使わない）
</avoid_over_engineering>

## 生成手順（対話型）

### Step 1: エンティティの洗い出し

- L1 の要求から扱うデータ（エンティティ）を列挙する
- 既存の foundation §2.4 にインライン記述があれば取り込んでから拡張する

### Step 2: 関係の整理（概念モデル）

- エンティティ間の関係・キーを Mermaid `erDiagram` で描く（主要な関係のみ。全カラムは書かない）

### Step 3: データライフサイクル

エンティティごとに以下をヒアリングして表にする:

- **発生**: いつ・何をトリガーにデータが増えるか
- **更新頻度**: どのくらいの頻度で変わるか（不変/日次/リアルタイム等）
- **増加ペース**: どの程度のペースで増えるか（目安で可）
- **保持・ローテーション**: いつまで持つか。ローテーション/アーカイブの方針
- **削除**: 削除の条件・方式（物理/論理）。法規制・監査要件（L1 §2.2）があれば従う

### Step 4: 整合性の判断基準

- トランザクション境界・一意性・参照整合性など「実装時に迷う判断」の基準を1行ずつ書く

### Step 5: foundation.md のポインタ化

`docs/l2_foundation/data.md` を書き出したら、foundation.md の §2.4 を1行ポインタに置換する:

```markdown
### 2.4 データモデル

→ `data.md` を参照（概念モデル・データライフサイクル・整合性の判断基準）
```

## 再生成モード（既存 data.md がある場合）

### 保持するもの（上書きしない）

| 対象 | 理由 |
|------|------|
| 確定済みのライフサイクル方針（保持期限・削除条件） | 運用・法規制に直結する判断。変更時は差分を提示して確認 |
| スキーマの正への参照パス | 実装との対応を壊さない |
| ユーザーが追記したメモ | 手動編集を尊重 |

### 再生成時の手順

1. 既存 data.md を読み、エンティティとライフサイクル方針を把握
2. L1/L2 との差分を分析
3. ユーザーに「何を更新するか」を確認し、該当箇所のみ再生成

## 完了後の案内

- 生成ファイルのパス（`docs/l2_foundation/data.md`）とエンティティ数を報告
- foundation.md §2.4 をポインタ化した旨を報告
- TODO箇所の数を報告
- 次のステップ: `/gen-l3`（フェーズ計画）または `/gen-code`（データ層実装時に data.md が参照される）
