# コード生成コマンド

<tri_ssd_context>
Tri-SSD（Tri-Layer Slice Spec Driven）はAI/LLMコードエージェントを前提とした仕様駆動開発。

レイヤー構造:
- L0: アイディア・ラフメモ（docs/l0_ideas/）- 任意
- L1: 要件（docs/l1_requirements/vision.md）
- L2: システム構成（docs/l2_foundation/foundation.md）
- L3: フェーズ（docs/l3_phases/PH-xxx.md）- 機能+受け入れ条件

ID形式: PREFIX-nnnn（REQ, PH, F）
</tri_ssd_context>

## 概要

L3 フェーズドキュメントを入力として、テストコードと実装コードを生成する。
テスト駆動で実装し、検証ループで品質を担保する。
**実装完了 = コード生成 + 全AC検証パス + L3ドキュメント更新（チェック・証跡記録）までを含む。Phase 6 完了前にコマンドを終了してはならない。**

## コード生成時の原則

<avoid_over_engineering>
- L3に書かれていない機能を追加しない
- 「念のため」のエラーハンドリングを過剰に入れない
- 既存コードのパターンに合わせる（新しいパターンを導入しない）
- 最小限の実装から始める
- 実装が1つしかないインターフェースを作らない（テスト差し替え用の外部依存のみ例外）
- 1-2箇所からしか呼ばれず外部公開しない処理を関数に切り出さない
- L2の設計方針（ファイル粒度）に従う
</avoid_over_engineering>

## 引数

- `$1` (必須): 対象ID
  - **PH-xxx**: フェーズID → フェーズ内の全機能を順番に実装
  - **F-xxx**: 機能ID → 特定機能のみ実装

### 使用例

```
/gen-code PH-0001                 # フェーズ全体を実装
/gen-code F-0001                  # 特定機能のみ実装
```

## 前提条件

- L3 フェーズドキュメントが存在すること
- プロジェクト設定ファイルが存在すること（package.json, pyproject.toml 等）

## 実行フロー

### Phase 1: コンテキスト収集

1. **L3ファイル特定**: Glob で `docs/l3_phases/**/*.md` を検索
   - PH-ID指定時: 該当フェーズファイルを読み込み
   - F-ID指定時: 該当機能を含むフェーズファイルを検索
2. L3 ドキュメントを読み込む
3. **プロジェクト設定を自動検出**:
   - `package.json` あり → `npm test`, `npm run lint`
   - `pyproject.toml` あり → `pytest`, `ruff check`
   - `go.mod` あり → `go test ./...`, `golangci-lint run`
   - 検出できない場合 → ユーザーに確認
4. **L2 確認**: `docs/l2_foundation/foundation.md` から技術スタック把握
   - セクション2.1（設計方針）から採用パターン・ファイル粒度を取得
   - セクション5（テスト・検証戦略）があれば、テストコマンド・検証ツールを取得
5. **既存コード確認**: Glob/Grep で関連ファイルを検索
   - 同名ファイルがある場合 → **再生成モード**へ

## 再生成モード（既存コードがある場合）

既存の実装/テストファイルがある場合は**再生成モード**で動作する。

### 再生成時の確認

```markdown
既存コードが見つかりました:
- テスト: tests/features/xxx.test.ts
- 実装: src/features/xxx.ts

どのように進めますか？
1. **全て再生成**: 既存を破棄し、L3から新規生成
2. **テストのみ再生成**: 実装は維持、テストを更新
3. **実装のみ再生成**: テストは維持、実装を更新
4. **差分確認**: L3との差分を表示してから判断
5. **キャンセル**: 何もしない
```

### Phase 2: 実装計画の確認

L3 から以下を抽出し、ユーザーに確認:

```markdown
## 実装計画

**対象**: [フェーズ名 / 機能名]
**検出した環境**: [package.json / pyproject.toml / etc.]

### 生成予定ファイル

| 種別 | パス | 説明 |
|------|------|------|
| テスト | tests/... | [概要] |
| 実装 | src/... | [概要] |

### 受け入れ条件 → テストケース

| AC | テストケース | 検証手段 |
|----|-------------|---------|
| AC-1 | [テスト概要] | テスト |
| AC-2 | [テスト概要] | コマンド実行 |
| AC-3 | [スナップショットテスト等] | 自動検証に置換を検討 |

（L3に `- 検証:` 行がないACはデフォルト「テスト」として扱う）
（`目視確認` のACがあれば、スナップショットテスト・DOMアサーション等で自動化できないか提案する）

### ファイル粒度チェック
L2の設計方針（セクション2.1）に照らして、生成予定ファイル数が適切か確認する。

この計画で進めますか？ (yes/no/修正)
```

### Phase 3: テスト生成

<thinking_process>
ファイルパス決定の判断基準:

1. **既存コードのパターンは？**
   - Glob で類似ファイルを検索し、配置パターンを推測
   - テストの配置: `tests/`, `__tests__/`, `*_test.py` 等

2. **インターフェース種別は？**
   - API → `src/api/`, `tests/api/`
   - UI → `src/components/`, `tests/components/`
   - CLI → `src/cli/`, `tests/cli/`
</thinking_process>

1. **ファイルパス決定**: 既存コードのパターンから決定
2. 受け入れ条件（AC）からテストコードを生成
3. 自動検出したテストツールを使用（jest, pytest 等）

**テスト生成の原則**:
- 受け入れ条件を忠実にテスト化
- 境界値・異常系も含める（L3に記載がある場合）
- モック/スタブは最小限

### Phase 4: コード生成

1. L3 の受け入れ条件を満たす実装を生成
2. 既存コードのパターンに合わせる

**コード生成の原則**:
- L3 の受け入れ条件に厳密に従う
- 既存コードのエラー処理パターンに合わせる

### Phase 5: 検証ループ

1. **Lint実行** → 失敗時は自動修正（--fix）して再実行
2. **テスト実行** → 失敗時はエラー分析・修正して再実行
3. **コマンド検証**（ACに `検証: curl ...` 等がある場合）→ Bashで実行し出力を検証
4. **最大3回失敗で中断**（circuit-breaker）

**検証手段別の処理**:

| 検証手段 | 処理 | 自動チェック |
|---------|------|-------------|
| テスト | テストランナーで実行 | Yes |
| コマンド実行 | Bashで実行し期待出力と比較 | Yes |
| 目視確認 | 自動化を提案→不可なら最後にユーザーに委任 | 原則No |

**目視確認ACへの対応**:
- まずスナップショットテスト、DOMアサーション、スクリーンショット比較等で自動検証に置換できないか検討・提案する
- 自動化できた場合: L3の `検証:` 行を自動検証手段に書き換え、テストを実行
- どうしても不可の場合のみ: ユーザーに確認を委任し、ACは未チェックのまま残す

**検証ループの原則**:
- 各反復でエラー内容を分析し、異なるアプローチを試す
- 同じエラーが続く場合は早期中断

**完了ゲート（Phase 6 に進む前の必須確認）**:
- [ ] 全テストがパスしている
- [ ] コマンド検証が全てパスしている（該当ACがある場合）
- 上記を満たさない限り Phase 6 に進まない（circuit-breaker で中断した場合はコマンド失敗として終了）

### Phase 6: L3 更新と証跡記録（必須・省略不可）

**このフェーズはコマンド完了の必須条件。Phase 5 をパスした場合、必ず以下を全て実行する。**

実装完了後、L3 フェーズドキュメントを更新:

1. **L3ファイルを再読み込み**して最新状態を取得
2. **受け入れ条件を1件ずつ検証結果と照合**:
   - テスト検証AC: 対応テストがパスしていれば `[x]` マーク + 証跡追記
   - コマンド検証AC: 実行結果が期待通りなら `[x]` マーク + 証跡追記
   - 目視確認AC（自動化に置換できなかった場合のみ）: 未チェックで残す
3. **Exit Criteria**: 該当項目に `[x]` マーク
4. **検証証跡を追記**: `- 検証:` 行に結果を記録
   - 例: `- 検証: テスト test_create_item がパス ✓ (2026-03-23)`
   - コマンド検証: 実行結果の要約を追記
5. **最終確認レポートを出力**:

| AC | 検証手段 | 結果 | L3更新 |
|----|---------|------|--------|
| F-0001 AC-1 | テスト | ✓ パス | [x] 済 |
| F-0001 AC-2 | コマンド | ✓ パス | [x] 済 |
| F-0002 AC-1 | テスト | ✓ パス | [x] 済 |

**L3ファイルの更新を確認するまでコマンドを完了としない。**

## 出力形式

### 成功時
- 生成ファイル一覧（テスト、実装）
- テスト結果サマリ
- L3 更新内容（チェックリスト完了）
- 次のステップ: `/archive-l3 PH-xxx` でアーカイブ（全フェーズ実装完了後）

### 失敗時
- エラー内容（最後のエラーログ）
- 試行した修正内容（3回分）
- 推奨アクション（L3見直し、手動デバッグ検討）

## 注意事項

- **既存コードの上書き確認**: 同名ファイルがある場合は再生成モードで対話確認
- **部分成功は認めない**: 全テスト通過 + 全AC検証 + L3更新が完了条件
- **Phase 6 スキップ禁止**: コード生成・テストパス後にL3更新せず終了することは許容しない

## 完了後の案内

- 生成ファイル一覧を報告
- テスト結果サマリを報告
- **AC検証結果レポート**（Phase 6 の最終確認レポート）を報告
- 未チェックACがある場合はその理由を報告（目視確認で自動化不可等）
- 全フェーズ実装完了後は `/archive-l3` でアーカイブを案内
